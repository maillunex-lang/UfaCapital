# Первый связанный вертикальный срез A

Цель: доказать общий рынок с выгодой специализации, а не продемонстрировать изолированные экраны. Один город Уфа; карта на реальной географической основе, без копирования чужого арта; expandable IDs/coordinates. Зерно→мука→хлеб→магазин; местная доставка, заявки и простой обеспеченный контракт. Мельница/пекарня/магазин/склад, агрегированные работники, расходы и базовый обеспеченный кредит. Минимум два настоящих человека и два разных ИИ.

## Приёмочный сценарий

1. Установить подписанный тестовый APK на Android. Два независимых аккаунта входят по HTTPS в staging VPS, видят один мир/Уфу. Отдельно проверяется веб-админ.
2. Игрок 1 открывает мельницу, закупает лимитированное зерно, нанимает штат и выпускает муку; игрок 2 открывает пекарню и покупает её на общем рынке.
3. Игрок 2 производит хлеб; ИИ-магазин или игрок 1 покупает/продаёт населению. Сделки видны обоим, ledger/остатки согласованы. Простой контракт подтверждён и доставлен.
4. Закрыть приложение владельца; производство/поставки продолжаются. Открыть снова, сверить снимок с сервером. Повтор timeout-запроса не удваивает расход.
5. Изменить публичные цены/спрос в контролируемом тесте. ИИ меняют поведение, память переживает рестарт. Отдельные сценарии доказывают все 14 возможностей, включая банкротство.
6. Обычный игрок не вызывает admin grants; тестовый администратор может выдать своей маркированной компании деньги/товар с проводкой и причиной. VIP выдаётся/истекает серверно, не меняет доходность.
7. Веб-админка меняет рецепт/коэффициент с effective_at; прошлые сделки не меняются. Загружает замену иконки товара с промптом/происхождением, публикует manifest, APK показывает замену; откат возвращает прежнюю.
8. Перезапуск сервера/БД сохраняет мир, повтор jobs не создаёт деньги/товар. Восстановление отдельной БД из backup подтверждено. Проверить задержку и журнал действий.

## Обязательное покрытие

| Требование | Где создаётся | Где доказывается |
|---|---|---|
| APK, аккаунты, landscape/map | F02 | F10 device + два человека |
| VPS/HTTPS/Compose/БД | F01/F09 | F09 restore/smoke, F10 network |
| VIP и игровой admin | F02 | role tests + F10 |
| Компании/предприятия/работники/кредит | F03/F04 | экономические тесты и F10 |
| Производство/склад/порча | F04 | invariant/restart + F10 |
| Рынок/доставка/контракт/население | F05 | race/API + F10 |
| Два ИИ и все 14 возможностей | F06 | сценарии/симуляция + F10 |
| Сохранение/офлайн/синхронизация | F01/F04/F08 | fault/reconnect + F10 |
| Админка всех настроек/аудит | F01–F07 в тех же задачах | matrix + browser E2E |
| Все графические ресурсы: промпт/замена | F07, записи с F02 | manifest completeness + Android swap/rollback |
| Автотесты критических операций | F03–F08 | CI evidence + F10 |

Что не входит: многогородность, корпорации/биржа долей, глубокий бренд/R&D, свободное строительство, макромодель C, сложная сеть будущих обязательств E, реальные платежи. Прототип требует рабочей VIP-системы с выдачей администратором, не платёжного процессора.

Выход F10 — отчёт со сборкой/version/hash, устройствами/Android, VPS environment, test run ссылками, двумя человеческими участниками (без публичных секретов/PII), доказательствами сценария и известными ограничениями. Отсутствие VPS/SDK/устройства/второго человека — BLOCKED для соответствующего доказательства, не «DONE по коду». Автоматические аккаунты не заменяют двух реальных людей в итоговой приёмке.
