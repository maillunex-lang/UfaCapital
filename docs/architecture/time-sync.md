# Серверное время, офлайн и восстановление

Время UTC сервера, экономика интервалами по 5 минут как исходная настройка. Первый выпуск в пределах одного интервала; никаких индивидуальных ускорителей. Фактическое время клиента не участвует в выпуске/штрафах/VIP.

Один владелец scheduler берёт PostgreSQL lock. Период имеет snapshot конфигурации и устойчивый номер. Фазы: (1) наступившие изменения/доставки/порча, (2) подтверждённые входы и резерв payroll/energy, (3) производство по сохранённому порядку, (4) ограниченные покупки населения, (5) платежи/обязательства и статусы несостоятельности, (6) агрегаты/agent decisions для следующего периода. Решения агентов исполняются обычными командами, не особым скрытым проходом.

Зарплата либо резервируется перед запуском партии и перечисляется в её операции, либо начисляется по отдельному согласованному расписанию; в срезе используется первый вариант, без двойного начисления в фазе 5. Обслуживание/аренда учитываются своим уникальным period key. Смена рецепта вступает на новой работе, не меняет уже запущенную. Порядок торговых операций фиксируется последовательностью сервера.

Не требуется одна огромная транзакция на весь мир. Каждая фаза хранит checkpoint, у jobs уникальный ключ (world,period,phase,entity); для job атомарны эффект и отметка выполнения. Если сервер упал после commit до уведомления, outbox и повтор команды возвращают прежний результат. Отказ между jobs продолжает период с сохранённого места. Завершённый job не проигрывается снова.

При отставании последовательно обрабатываются интервалы ограниченными пачками, с метрикой lag; нельзя сворачивать несколько дней в «доход по формуле» и пропускать порчу/доставки. При крупном отставании (>24 ч как начальный операционный порог) мир переводится в maintenance, восстанавливается в изолированной среде; решение о переносе дедлайнов публикуется и аудируется. Нет тайного штрафования игроков за недоступность сервера.

Клиент после login получает snapshot с cursor. Затем polling/events или WS. Снимок и cursor согласованы транзакционно; событие не теряется между ними. Duplicate игнорируется; gap/expired cursor вызывает новый snapshot. Оптимистичный UI допустим только для состояния «запрос отправлен», баланс до серверного подтверждения не считается окончательным.

Вход в игру не начисляет офлайн-доход. Бесплатные автопоручения имеют max_price, budget, min_cash, target_stock и срок; каждая покупка — обычная команда. При отсутствии денег, сырья, места или разрешения предприятие останавливается с причиной. Испытания: restart в каждой фазе, повтор outbox, большой clock skew клиента, повтор snapshot и deadline во время обслуживания.
